# TRIZ 분석

모순을 풀어 해결 아이디어를 도출한다. **기술적 모순**(두 특성의 상충)은 모순 행렬과 40 발명 원리로, **물리적 모순**(한 특성에 상반된 요구)은 분리 원리로 푼다.

## 원칙 (반드시 지킨다)

- **판단은 당신(LLM), 조회는 데이터 파일.** 조회는 `<skill-dir>/data/`의 파일을 Read 도구로 직접 읽는다(`<skill-dir>`은 스킬이 로드될 때 알려주는 base directory). 행렬 셀 값, 원리 번호, 원리 이름·하위 원리, 파라미터 정의, 분리 유형과 연계 원리는 **오직 `data/`의 파일이나 `references/`에서만** 가져온다. 기억으로 만들거나 고치거나 보간하지 않는다.
- 읽은 값의 번호·이름·횟수는 그대로 인용한다. 순위를 바꾸거나 원리를 추가·삭제하지 않는다.
- 답안에 조회 결과의 출처를 적을 때는 **실제로 읽은 파일**만 적는다. 읽지 않은 파일을 읽은 것처럼 쓰지 않는다.
- 출력 언어는 사용자 입력 언어를 따른다. 파일 안의 `ko`/`en` 필드 중 사용자 언어의 것을 고른다.
- 아이디어는 사용자의 실제 시스템에 맞춰 구체적으로 쓴다. 원리 문장을 되풀이하지 않는다.

## 데이터 조회

필요한 파일만 읽는다. 폴더 전체나 쓰지 않는 파일을 읽지 않는다.

| 조회 대상 | 파일 | 읽는 값 |
| --- | --- | --- |
| 행렬 셀 | `data/matrix/row-<개선 번호 2자리>.json` | `cells["<악화 번호>"]` (원리 번호 목록) |
| 원리 | `data/principles/p-<번호 2자리>.json` | `name`, `sub_principles`, `cases` |
| 파라미터 | `data/parameters.json` | 이름, 정의, 키워드 |
| 분리 원리 | `data/separation-principles.json` | 유형별 `question`, `related_principles` |

- **행 파일은 개선 파라미터, 셀 키는 악화 파라미터다.** 예: 개선 #9, 악화 #19 → `data/matrix/row-09.json`을 열고 `cells["19"]`을 읽는다. 개선·악화를 뒤바꾸면 다른 셀이 나온다.
- `cells`에 악화 번호 키가 없으면 "행렬에 원리가 없는 조합"이다. 비어 있다고 보고 추측해서 채우지 않는다.
- 번호는 2자리로 맞춘다(`row-09.json`, `p-05.json`).

### 순위 집계 (손으로 한다. 아래 순서를 그대로 따른다)

1. 조합(개선, 악화)마다 셀(원리 번호 목록)을 만든다. 조합 순서는 개선 후보 순서이고, 그 안에서 악화 후보 순서다. 빈 셀은 건너뛴다. 이 순서가 셀 순서다.
2. 원리마다 등장한 셀 수(count)를 센다. 한 셀에 같은 원리는 한 번만 있다.
3. count가 큰 원리가 앞선다.
4. count가 같으면 "가장 앞선 위치"로 정한다. 위치는 (셀 안 순번, 셀 순서)다. 셀 안 순번이 작은 쪽이 앞선다. 같으면 셀 순서가 앞선 쪽이 앞선다. 원리가 여러 셀에 있으면 그중 가장 앞선 위치를 쓴다.
5. 상위 3~5개를 고른다. 표의 count는 2단계 값을 그대로 쓴다.

예: 셀 A = [8, 15, 35, 38], 셀 B = [14, 20, 19, 35]. #35는 두 셀에 있어 count 2로 1위다. 나머지는 count 1이다. 위치로 정렬하면 #8(0번째, A), #14(0번째, B), #15(1번째, A), #20(1번째, B), #19(2번째, B), #38(3번째, A) 순이다.

분리 원리 순위도 같은 절차다. 셀 대신 고른 분리 유형의 `related_principles` 목록을 쓴다. 목록은 고른 유형 순서대로 놓는다.

## 1. 유형 판별

| 유형 | 판별 기준 | 처리 |
| --- | --- | --- |
| 기술적 모순 | 서로 다른 두 특성이 상충 ("A를 개선하면 B가 악화") | 2장 절차대로 진행 |
| 물리적 모순 | 하나의 특성에 상반된 요구 (커야 하고 작아야 함) | 3장 절차대로 진행 |
| 해법 설명 | 문제 대신 이미 만든 해법을 설명 (특허 초록, 제품 소개) | 모순이 드러나 있지 않다. 추측하지 말고 1.1 인터뷰의 질문 1~3으로 그 해법이 어떤 트레이드오프를 풀었는지 묻는다 |
| 모호한 입력 | 목표·제약이 불명확, 또는 모순이 드러나지 않음 | 1.1 구조화 인터뷰로 모순을 도출한 뒤 이 표로 돌아와 다시 판별 |

### 1.1 구조화 인터뷰

모순을 만들 정보가 모자랄 때 쓴다. **질문은 한 번에 하나**, 전체 **최대 5개**. 이미 입력에 답이 있는 질문은 건너뛴다.

1. 개선하려는 시스템은 무엇이고, 무엇이 좋아지길 원하는가?
2. 지금까지 시도했거나 떠올린 해결책은 무엇인가?
3. 그 해결책을 쓰면 무엇이 나빠지는가? (또는: 무엇 때문에 그 해결책을 쓸 수 없는가?)
4. 지켜야 하는 제약은 무엇인가? (비용, 규격, 공정, 일정 등)
5. 답을 모아 모순 문장을 만들고 "이렇게 정리했는데 맞는가?"로 확인한다.

- 3번의 답이 "다른 특성이 나빠진다"면 기술적 모순, "같은 특성이 반대로 필요하다"(예: 두꺼워야 하는데 얇아야 한다)면 물리적 모순이다. 1장 표로 돌아가 판별한다.
- 5개를 다 물어도 모순이 안 나오면 억지로 만들지 않는다. 지금까지의 답을 요약하고 무엇이 더 필요한지 말한다.
- 사용자가 질문하지 말고 진행하라고 했으면 인터뷰를 생략한다. 입력에서 가장 그럴듯한 모순을 세워 진행하되, 모순 정의 끝에 "(입력에서 추정한 모순. 확인되지 않음)"을 붙이고 "다음 단계"에 확인할 질문을 적는다.

### 1.2 사례 사용

원리 파일의 `cases`는 다른 분야에서 같은 하위 원리로 상충을 푼 예다. 사용자 시스템의 무엇이 사례의 무엇에 대응하는지 따져 **비유로만** 쓰고, 아이디어는 사용자 시스템에 맞춰 새로 쓴다. 사례를 그대로 옮겨 아이디어로 내놓지 않고, 언급할 때는 "(사례: `domain_name`)"처럼 밝힌다. 맞는 사례가 없으면 쓰지 않는다.

## 2. 기술적 모순 절차

1. **모순 문장화** — "[시스템]의 [개선 특성]을 높이면 [악화 특성]이 나빠진다" 형식으로 다시 쓰고 사용자에게 확인받는다. 확인 전에는 다음 단계로 가지 않는다.
2. **파라미터 매핑** — 이 단계에서만 `references/parameters-39.md`를 읽는다. 개선·악화 각각 후보 1~3개를 고르고 근거를 한 줄씩 붙인다. 애매하면 `data/parameters.json`에서 해당 파라미터의 정의를 읽어 확인한다. 39개 중 맞는 것이 없으면 억지로 고르지 말고 사용자에게 다시 묻는다.
3. **행렬 조회** — 개선·악화 후보 조합(최대 3×3=9쌍)마다 해당 행 파일을 읽고 `cells`의 셀을 얻는다. 개선 후보와 악화 후보에 같은 번호가 있으면 6장대로 처리한다. 같은 개선 후보의 행 파일은 한 번만 읽는다.
4. **원리 집계** — "순위 집계" 절차로 `ranking`(빈도 내림차순)을 만들고 상위 3~5개를 순서대로 고른다.
5. **원리 정의 조회** — 고른 원리의 `data/principles/p-NN.json`을 읽어 이름, 하위 원리, 산업 사례를 얻는다.
6. **아이디어 생성** — 원리마다 사용자 시스템에 맞춘 적용안 1~3개를 쓴다. 하위 원리 중 어느 것을 적용했는지 드러나게 한다. 사례는 1.2를 따른다.
7. **출력** — 4장 포맷으로 정리한다. 예시는 `references/workflow-examples.md`.

## 3. 물리적 모순 절차

이 절차를 시작할 때 `references/physical-contradiction.md`를 읽는다.

1. **모순 문장화** — "[대상]의 [특성]은 [이유 A] 때문에 [P]여야 하고, [이유 B] 때문에 [반대 P]여야 한다"로 쓰고 사용자에게 확인받는다. 대상은 모순이 걸린 구체적 요소로 좁힌다. 두 특성이 서로 다르면 물리적 모순이 아니므로 2장으로 간다.
2. **분리 축 확인** — `data/separation-principles.json`을 읽어 5종의 `question`을 얻는다. 각 요구가 **어디서, 언제, 누구·무엇에 대해, 어느 방향으로, 어느 수준에서** 필요한지 확인한다. 입력에 답이 없으면 사용자에게 **한 번에 하나씩** 묻는다(가장 결정적인 축부터, 최대 3개).
3. **분리 유형 선택** — 두 요구가 겹치지 않는 유형을 1~2개 고르고 근거를 한 줄씩 쓴다. 어느 축에서도 겹치면 `system`(시스템 수준)을 고른다.
4. **원리 조회** — 상위 원리 3~5개를 **순서대로** 고른다(순서를 건너뛰지 않는다).
   - 여러 유형: **가장 잘 맞는 유형을 먼저** 놓고, "순위 집계" 절차로 `ranking`(빈도 내림차순)을 만들어 고른다.
   - 한 유형: 그 유형의 `related_principles`를 파일에 적힌 순서대로 고른다. 2단계에서 이미 읽었으면 다시 읽지 않아도 된다. 이때 출처는 "`separation-principles.json`의 [유형]"으로 적는다.
5. **원리 정의 조회** — 고른 원리의 `data/principles/p-NN.json`을 읽는다.
6. **아이디어 생성** — 원리마다 적용안 1~3개. 어떤 분리(예: "비가 올 때만 크게")를 구현하는지 드러나게 쓴다. 사례는 1.2를 따른다.
7. **출력** — 4장의 물리적 모순 포맷.

## 4. 출력 포맷

```markdown
## 모순 정의
[시스템]의 [개선 특성]을 높이면 [악화 특성]이 나빠진다.

## 파라미터 매핑
| 구분 | 파라미터 | 근거 |
| --- | --- | --- |
| 개선 | #9 속도 | ... |
| 악화 | #19 에너지 사용 (움직이는 물체) | ... |

## 추천 원리 (행렬 조회 결과)
| 순위 | 원리 | 등장 횟수 |
| --- | --- | --- |

## 적용 아이디어
### 원리 #10 사전 조치
- 아이디어 1: ...

## 다음 단계
- 매핑 재검토가 필요한 지점, 검증 방법
```

물리적 모순이면 "모순 정의"와 "파라미터 매핑" 대신 아래 두 절을 쓰고, "추천 원리"의 제목은 "(분리 원리 조회 결과)"로 바꾼다.

```markdown
## 모순 정의 (물리적 모순)
[대상]의 [특성]은 [이유 A] 때문에 [P]여야 하고, [이유 B] 때문에 [반대 P]여야 한다.

## 분리 유형
| 유형 | [P]가 필요한 경우 | [반대 P]가 필요한 경우 | 판단 |
| --- | --- | --- | --- |
| 시간에 의한 분리 | 비가 올 때 | 보관할 때 | 겹치지 않음 → 선택 |
```

"추천 원리" 표는 집계 결과(번호·이름·횟수)를 그대로 옮기고, "적용 아이디어"만 직접 작성한다.

## 5. 보고서 저장

사용자가 결과 저장을 요청하거나("저장해줘", "보고서로", "save") `/triz`에 `--save`가 붙어 있으면, 분석을 마친 뒤 결과를 Markdown 파일로 저장한다. 요청이 없으면 저장하지 않는다.

- **경로**: 사용자가 경로를 주면 그대로 쓴다. 없으면 현재 작업 디렉토리의 `triz-report-YYYYMMDD-<주제>.md`. `<주제>`는 시스템 이름을 소문자·하이픈으로 줄인 것(예: `triz-report-20260924-umbrella.md`)이다. 같은 이름의 파일이 있으면 덮어쓰지 말고 `-2`, `-3`을 붙인다.
- **내용**: 맨 위에 아래 머리말, 그다음 4장 포맷의 분석 전체를 채팅 출력과 **같은 내용**으로 넣는다. 인터뷰를 했다면 질문과 답을 "## 인터뷰 기록" 절로 덧붙인다.

```markdown
# TRIZ 분석 보고서: [주제]

- 작성일: YYYY-MM-DD
- 모순 유형: 기술적 모순 | 물리적 모순
- 원래 입력: > [사용자 입력 원문]
- 도구: triz-solver (읽은 데이터 파일: 예 `data/matrix/row-09.json`, `data/principles/p-35.json`)
```

- 저장한 뒤 파일 경로를 한 줄로 알린다. 파일을 쓸 수 없는 환경이면 보고서 전체를 Markdown 코드 블록으로 보여 주고 직접 저장하라고 안내한다.

## 6. 예외 처리

**빈 셀** — 오류가 아니다. 그 조합에는 행렬에 원리가 없다는 뜻이다. 일부만 비었으면 나머지 셀로 진행하고, 어떤 조합이 비었는지 한 줄로 알린다. 전부 비면 파라미터 재매핑을 **1회** 제안한다(다른 후보 또는 더 넓은/좁은 특성). 그래도 비면 원리를 지어내지 말고 결과가 없다고 말한다.

**`unverified` 키** — 행 파일에 `unverified`(악화 번호 목록)가 있으면, 그 악화 번호의 조합은 자료 간 값이 달라 확정하지 못한 셀이다. `cells`에 값이 있어도 비었다고 취급하고 쓰지 않는다. "이 조합은 검증된 데이터가 없어 조회할 수 없다"고 사용자에게 알리고, 가능하면 근접한 다른 파라미터(예: 움직이는/고정된 쌍의 다른 쪽)로 재매핑을 제안한다.

**파일을 읽을 수 없을 때** — 파일이 없거나 읽기에 실패하면 값을 기억으로 대신하지 않는다. 읽을 수 없는 파일 경로와 함께 조회할 수 없다고 사용자에게 알린다.

**번호 확인** — 파일을 읽기 전에 SKILL.md가 직접 확인한다.
- 파라미터 번호는 1~39, 원리 번호는 1~40이다. 범위 밖이면 번호를 다시 확인한다.

같은 오류가 두 번 반복되면 멈추고 사용자에게 상황을 알린다.
